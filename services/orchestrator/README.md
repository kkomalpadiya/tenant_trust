# Security action orchestration

`@tenant-trust/orchestrator` owns the closed-loop security-action boundary. T9.1 defines the executable state machine, and T9.2 defines trigger severity, independent corroboration and recovery eligibility.

Only a contract-valid `QUARANTINE` decision with an explicit `restrict-access` or `suspend-subject` obligation maps directly to reversible containment. `ALLOW`, `STEP_UP` and `DENY` do not mutate durable security state. One fresh severe signal can block renewal, while revocation requires two sources, two actionable critical kinds and a matching low-band T6.6 critical transition. Score movement alone can never revoke.

Recovery reuses the T6.6 two-source/two-evaluation controls. Restricted access needs a recovered medium band at score 45; suspension, renewal blocking and replacement after revocation need a recovered high band at score 75. Active severe evidence blocks recovery, and revocation recovery requires the cause to be resolved. T9.6 now converts eligibility into a five-minute authorization only after a current tenant administrator presents a request/session-bound, single-use `tenant:admin` step-up proof.

The model keeps access, renewal and certificate posture separate. Restriction, suspension and renewal blocking are reversible. Revocation permanently leaves the target certificate revoked. Recovery from revocation first issues a distinct replacement certificate and may then restore subject access; it never reactivates the revoked certificate.

T9.3 persists authorized actions, claims them with expiring leases, retries failures under the same stable action ID, and stores attempt plus terminal state. Reversible database controls complete atomically; certificate revocation requires an injected T3.7 executor and exact issuer confirmation before the database accepts success. T9.4 records authenticated lifecycle feedback without recursive action eligibility. T9.5 atomically queues session/cache invalidation when suspension or revocation succeeds, removes exact tenant-and-subject-scoped Redis entries under an idempotency marker and records the enforcement delay. T9.6 stores the exact recovery checkpoint and state version, consumes administrator step-up atomically, and requires a distinct active replacement certificate before a separately authorized access restoration. T9.7 automatically captures immutable requested, failed and succeeded action expectations for the separate audit projector, including governed recovery and certificate-event causation. T9.8 rejects competing recovery authorizations for the same checkpoint, suppresses stale recovery and already-satisfied actions before external execution, and gives outstanding severity work precedence over recovery.

Run `npm run security-action-state-machine:verify` for T9.1, `npm run security-action-rules:verify` for T9.2, `npm run security-action-orchestration:verify` for T9.3, `npm run security-state-invalidation:verify` for T9.5, `npm run security-recovery:verify` for T9.6, `npm run security-action-audit:verify` for T9.7 and `npm run security-action-adversarial:verify` for the integrated T9.8 replay, oscillation and conflict gate.
